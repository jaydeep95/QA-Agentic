3. What the Unified Application Understanding Means

The Unified Application Understanding is the durable semantic model of the AUT. It should be versioned and tied to evidence. It is not merely a generated "understanding document".

Structure

Screens, pages, components, fields, APIs, backend services, data entities and configuration.

Relationships

Frontend → API, API → service, service → data, navigation, dependencies, protection and other meaningful relationships.

Behaviour

Rules, validations, permissions, states, transitions, conditions, errors and observable runtime behaviour.

Grounding

Evidence, provenance, inference type, reconciliation state, oracle status and confidence.

Architecture invariant No downstream artifact is generated against an implicit or unversioned application context. Every generated artifact identifies the understanding version from which it was produced.

7. Quality, Evidence and Governance

Evidence and confidence

Evidence

What was actually observed or extracted, with a durable anchor.

Inference type

Deterministic, derived, or semantic.

Reconciliation

How static and runtime evidence relate: match, runtime-only, static-only, different, conflict, unverified.

Confidence

A platform-computed score exposed as Mostly Confident, Somewhat Confident, or Insufficient Evidence.

Evaluation is layered

LayerExamples
DeterministicSchema validity, duplicate detection, reference integrity, coverage arithmetic, locator validation, generated-code checks.
DerivedArtifact consistency, lineage integrity, contradiction detection, data/constraint compatibility.
SemanticScenario quality, missing edge cases, expected-result quality, diagnostic interpretation.

One governance model

Human and autonomous operation
flowchart LR
  G["Generate"] --> E["Evaluate"]
  E --> X{"Governance Gate"}
  X -->|Human| H["Approve / Edit / Reject"]
  X -->|Autonomous| P["Policy: Continue / Stop / Escalate"]
  P -->|Escalate| H
  H --> NEXT["Next stage"]
  P --> NEXT

Autonomous mode is not a separate quality path. It changes the decider at the gate while retaining evaluator, evidence, safety and policy controls.

Coverage

The platform should pursue very high coverage through explicit obligations rather than an LLM-generated percentage.

D1. Static Understanding — Architecture Detail

Static understanding is the first evidence source and establishes the baseline model before runtime enrichment.

Static understanding

  R["Repo set + pinned revisions"] --> I["Ingestion"]
  I --> D["Stack detection / framework pack"]
  D --> X1["Entities"]
  D --> X2["Schema / constraints"]
  D --> X3["Rules / permissions"]

Static analysis is expected to be strong for structural inventory and schema extraction, while cross-layer relationships and some business behaviour remain more uncertain. The architecture therefore preserves uncertainty instead of flattening all output into "facts".

D2. Runtime Exploration — Architecture Detail

The platform owns the exploration agenda, state model and safety decisions. The crawler provider owns browser actuation and observation collection.

Runtime exploration
flowchart TB
  U["Baseline Understanding"] --> P["Exploration Planner"]
  P --> G["Safety / Environment Policy"]
  G -->|allowed| S["Exploration Session"]
  S --> O["Observe state"]
  O --> A["Select next action"]
  A --> C["CRAWLER_PROVIDER"]
  C --> R["Runtime observation"]
  R --> SI["State identity"]
  SI --> UP["Update runtime model + agenda"]
  UP --> O
  P -->|blocked| B["Blocker / Escalation"]
  UP --> FIN["Session result"]

Runtime exploration should default to safe behaviour for unknown or destructive actions. It should be possible to stop, resume, audit and explain why an exploration step was or was not attempted.

D3. Reconciliation — Architecture Detail

Static versus runtime
flowchart TB
  S["Static evidence"] --> R["Reconciliation"]
  T["Runtime evidence"] --> R
  R --> M1["Match"]
  R --> M2["Runtime only"]
  R --> M3["Static only"]
  R --> M4["Different"]
  R --> M5["Conflict"]
  R --> M6["Unverified"]
  M2 --> U["Extend understanding"]
  M3 --> H["Hold / explore further"]
  M4 --> Q["Quality / mismatch analysis"]
  M5 --> F["Defect candidate when corroborated"]
Mismatch ≠ defect. A mismatch is first a reconciliation result. It becomes a defect candidate only after the platform establishes that the evidence is comparable and the difference is not explained by incomplete exploration, stale context, environment/configuration or declared variation.

D5. Traceability and Artifact Lineage

Artifact lineage
flowchart LR
  RV["Repository / runtime evidence"] --> U["Understanding Version"]
  U --> SC["Scenario"]
  SC --> TC["Test Case"]
  TC --> DR["Data Requirement"]
  TC --> AS["Automation Specification"]
  AS --> AB["Automation Binding"]
  AB --> EX["Execution"]
  EX --> EV["Evaluation"]
  EV --> FN["Finding"]
  FN -. new evidence .-> U

Each artifact is versioned and carries its parent/context version. A human edit creates a new version rather than mutating the machine-generated original. Approved artifacts are immutable.

Why this matters

  • Impact analysis when application source changes.
  • Explanation of why a test exists.
  • Reproducibility of generation.
  • Safe regeneration when understanding changes.
  • Run-over-run comparison without relying on array position or UI ordering.
