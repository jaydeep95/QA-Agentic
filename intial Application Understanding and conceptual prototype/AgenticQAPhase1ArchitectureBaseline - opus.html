Level 1Architecture Overview

Readable end to end in a few minutes. Nothing here depends on the detail sections that follow.

1Architecture at a Glance

The platform builds and maintains a durable, evidence-backed understanding of the application under test, then generates everything else from it.

Source repositories are analysed to produce a baseline Unified Application Understanding — the platform's model of the application's screens, components, fields, APIs, services, data, relationships, rules, permissions and states. Where a running instance is available, runtime exploration observes the real application and reconciliation determines how those observations relate to what the source predicted. Everything downstream — coverage obligations, scenarios, test cases, test data, Playwright automation, execution and findings — is generated from that understanding, against a named version of it, and remains traceable back to the evidence that justified it.

Around this spine sit cross-cutting platform capabilities: evidence and provenance, evaluators and confidence, governance for human and autonomous decisions, and a single integration path for external providers. Heavy or hostile workloads — code analysis, browser exploration, test execution — run in isolated workers, while the core platform stays a modular, independently evolvable whole.

The architecture in one statement

A modular QA platform built around a versioned Unified Application Understanding, combining static source understanding with optional runtime exploration and reconciliation. Independent test-design, test-case, automation, execution and evaluation components consume that understanding through explicit contracts. External capabilities such as Code Intelligence and the Crawler remain replaceable providers. Evidence, confidence, governance and traceability are cross-cutting. Heavy browser and analysis workloads run in isolated workers, while the core platform remains modular and independently evolvable.

2Architectural Drivers

Four forces shaped every decision in this document. Everything else follows from them.

1 · Understanding is the product asset

Tests are regenerable; the understanding is not. It must be durable, versioned, evidence-backed and queryable — so it is modelled first and everything else derives from it.

2 · Two sources of truth must combine

Source code gives breadth and structure; the running application gives behavioural ground truth. Neither alone is sufficient, and their disagreements are valuable rather than noise.

3 · Nothing may be asserted without support

Evidence, provenance, inference type, oracle status and confidence are modelled data, not presentation. The platform must be able to say "insufficient evidence" instead of inventing certainty.

4 · Every part must be replaceable

Providers, techniques, evaluators and whole components will change across phases. Contracts are placed so that change stays local.

4Unified Application Understanding

The central product asset. Everything the platform generates is generated from it, against a named version of it.

What it holds

Application structure

Entities · screens and pages · components · fields · APIs · backend services · data structures

Relationships

Navigation · component composition · frontend-to-backend call paths · service and data dependencies · cross-repository links

Behaviour

Validations · business rules · permissions and roles · states · transitions · error paths

Grounding

Evidence · provenance · inference type · oracle status · reconciliation status · confidence · version

Every element carries its own grounding. A screen is not simply "known to exist" — it is known on the basis of specific evidence, reached by a specific kind of inference, confirmed or not confirmed at runtime, and carried at a stated confidence. This is what allows the platform to distinguish what it has verified from what it has assumed.

Architecture invariant Fixed

No downstream artifact is generated against an implicit, unversioned or unknown application context.

Every scenario, test case, data requirement, automation specification and execution names the Understanding version it was generated from. When that understanding changes, the platform can identify exactly what is now stale — and staleness is surfaced for a decision, never silently auto-resolved.

The canonical semantic model is the Unified Application Understanding: the application as the platform understands it. Fixed

The internal representation — how that model is physically recorded so it can carry provenance, versioning and contradiction — is a separate concern. The baseline records it as versioned, evidence-backed assertions with stable content-derived identity, which makes understanding-diff, corroboration and reconciliation ordinary set operations. That technique is sound and recommended, but it is an implementation of the model rather than the model itself. Flexible — see D1.

Runtime exploration is valuable, not mandatory Fixed

The platform produces useful output from static evidence alone. Exploration may be unavailable, restricted by policy, blocked on a prerequisite, or deliberately switched off — and in every one of those cases understanding is still built, scenarios and test cases are still generated, and automation is still produced. What changes is the validation level: unconfirmed elements are marked unverified, locators remain unvalidated, confidence is lower, and coverage reports a larger insufficient-evidence share. Downstream components are required to handle unverified input; none of them may treat runtime confirmation as a precondition.

Operating modes Flexible

Static only

No running instance. Full pipeline runs; locators are candidates; confidence capped; coverage reports unverified obligations honestly.

Static + exploration

The intended default. Runtime confirms relationships and locators, raises confidence, and surfaces reconciliation differences.

Continuous

Re-analysis on new revisions and periodic re-exploration; understanding diffs drive staleness and regeneration decisions.

Architecture principle Fixed

Self-healing may repair how an element is found. It may never change what the test means.

Business intent, assertion semantics, acceptance criteria and test purpose live in the specification, which the healing path cannot reach. Every healing action is evidence-backed, policy-controlled, auditable and reviewable. Default policy proposes rather than applies; auto-apply is a per-workspace setting enabled on measured evidence, not a rewrite of the design.

Execution Fixed

Real Playwright execution runs in isolated workers, never inside the API process. Four concerns are configured independently of test content:

Environment

A first-class entity per workspace: base URL, allowed domains, credential references, data-safety class, reset capability, concurrency ceiling. Automation contains no environment values.

Secrets

References everywhere; resolved once inside the worker at job start; redacted from logs; never placed in generated code, artifacts or model prompts.

Workers

Container-isolated, holding no database credentials, posting results through a narrow callback. Browser instability cannot reach the platform.

Concurrency

Three ceilings compose — global pool, per-environment protection, per-run user setting — and the effective limit is the minimum, so the user-facing control is always safe.

Retries are classified before they are attempted: infrastructure faults retry automatically, assertion failures never do, and a locator failure may retry once with healing if policy allows — recorded as a distinct attempt so flakiness stays visible rather than being smoothed away. Execution artifacts (traces, video, screenshots, network and console logs) are collected as evidence and stored by reference. Details in D8.

7Governance & Quality

Coverage, evaluation, confidence and approval are cross-cutting platform mechanisms — defined once and applied to every generated artifact, rather than rebuilt inside each stage.

Measurable coverage

The platform is designed to systematically pursue very high coverage using multiple complementary test-design techniques. Coverage is measured against explicit obligations derived from the understanding and reported with evidence, uncovered areas and insufficient-evidence gaps — rather than presented as an unqualified percentage. No model is asked what the coverage is, and no model can assert it. Fixed

Test data and state provisioning are different things Fixed

A test case declares data requirements; it never contains resolved data. Resolution happens at bind time, against a specific environment, through an ordered ladder — and each rung records why the previous one was insufficient.

D1Understanding model — internal representation, identity, lineage

The Unified Application Understanding is the canonical model. This section describes how it is physically recorded so that it can carry provenance, versioning and contradiction. Flexible — the technique is recommended and proven, but it implements the model rather than defining it.

Layers of the representation

LayerIsIs not
EvidenceAn immutable, anchored record that something was observed at a point in time, in a version of the world. Static (repository, revision, path, symbol, span, content hash), runtime (session, step, URL, DOM hash, network event, artifact reference), provider (invocation identity and version) or execution (attempt, result, artifact).An interpretation. Evidence carries no confidence — it either resolves or it does not.
ObservationStructured output from an extractor or provider before normalisation. Retained for reprocessing.Canonical. Nothing downstream reads it.
AssertionA normalised statement about the application, supported by one or more evidence records, carrying inference type, oracle status where applicable, reconciliation status and computed confidence.A fact. It may be wrong, superseded, contradicted or unverified — and the model records which.
Understanding versionA named snapshot pinning the repository tuple, the exploration sessions included, and the assertion set.A branch. Versions are linear per workspace and immutable once referenced.

Content-derived identity

Each assertion carries an identity computed from its normalised subject, relation and object — a route template, an endpoint method and path, a symbol's qualified name — never from a database key, file offset or extraction order. Four capabilities follow from this one choice:

  • Understanding diff across revisions is a set difference.
  • Reconciliation is the intersection and difference of two populations sharing one key space, so the same fact observed statically and at runtime collides by construction rather than by fuzzy matching.
  • Corroboration is natural — two extractors producing the same key means two independent evidence records on one assertion, which is precisely the signal confidence needs.
  • Stable comparison across regeneration, which removes the identity fragility of index-based matching.
Known cost

Identity is only as stable as the normalisation producing it. Renaming a route, endpoint or symbol reads as replace rather than rename. Phase 1 implements heuristic rename detection for routes and endpoints and reports other churn honestly; an incomplete diff is preferable to a misleading one.

The four measured failure causes, and the rule each produces

Unresolved dynamic segments

A template segment collapsed to a wildcard matched every single-segment endpoint; one call site produced six wrong relationships. Rule: an unresolvable segment yields an assertion marked unresolved and participates in no match.

Framework routing semantics

Literal paths matched a parameterised route the framework would never select, because registration order and first-match-wins were not modelled. Rule: route matching is delegated to a framework pack modelling the real resolution algorithm.

Transitive reachability

A screen inherited four endpoints through an import chain it never calls. Rule: direct calls and transitive reachability are different relations with different confidence; reachability alone never produces a call relation.

Injected services, erased types

Five screens produced no relation at all because they receive a running service as a prop and import only types, which vanish at runtime. Rule: statically unresolvable by construction — flagged unverified and handed to exploration, where one observed request settles it.

Framework packs

The extensibility unit for static analysis. A pack bundles, for one framework family, the route-registration model, client-call idioms, component and handler conventions, validation library shapes and locator conventions. Packs are versioned and independently evaluable, so a new stack is an additive unit of work with its own measured quality figure rather than a rewrite of the pipeline.

Incremental rescan

A new revision triggers a diff-scoped rebuild: changed files determine which extractors rerun; unchanged assertions carry forward with evidence re-anchored where content hashes match. Assertions whose supporting evidence no longer resolves become stale and cascade a staleness marker to every artifact derived from them. Staleness is surfaced for a governance decision, never auto-resolved.

Action risk classification Fixed

Because the understanding already knows which endpoint a control invokes and with which verb, risk is classified before the action occurs. A control whose handler calls a delete endpoint is classified destructive and blocked by policy without being pressed.

Classes: read (navigation, queries) · benign write (creates and updates within the workspace) · destructive (deletes, cancellations, irreversible transitions) · external effect (payments, email, third-party calls) · unknown (target undeterminable). Policy sets permitted classes per environment; unknown defaults to not permitted and becomes an agenda item requiring escalation rather than a gamble.

Blockers

When exploration cannot proceed — a required identifier, a one-time code, a document upload, an entity that must already exist — it emits a durable, attributable, resumable work item stating what is required, why, which resolution strategies were attempted and why each was insufficient. Supplied values are classified on arrival as secret, personal data, test data or entity reference and routed accordingly; a value classified secret is stored as a reference and never enters an artifact, a log or a prompt regardless of which field it was typed into.

Mismatch is not defect

Four deterministic checks run before any semantic judgement: was the area within exploration coverage; are both observations from the same revision and environment; is the difference within a declared variation allowance; is there sufficient evidence on both sides. Language model provider

Model access separates into five concerns that are frequently and damagingly merged:

  • Task definition — the reasoning required, in domain terms, with a typed output contract. Owned by the domain.
  • Prompt assembly — versioned templates plus a context bundle drawn from the understanding. The prompt version is recorded on every artifact produced.
  • Model routing — task-to-model policy with declared fallbacks; a cheaper model for classification, a stronger one for design work.

Healing algorithm

On a locator resolution failure: capture the current DOM as evidence; search alternative candidates for the same semantic element reference, drawing on the understanding and prior runtime observations; probe each candidate; score the best replacement on strategy stability and semantic equivalence to the original reference; apply only if policy permits. The event is recorded either way, with before, after, evidence and score.

Phase 1 default: propose, do not apply. The full capability is implemented and exercised; only the application policy is conservative, because healing precision is unmeasured until Validation E and a platform whose promise is evidence should not silently rewrite its own tests before it can show the rewrites are right. Enabling auto-apply later is a per-workspace policy change, not an architectural one.

Environment

A first-class configured entity per workspace: base URL, allowed domains, credentials as references, data-safety class (read-only, mutable, disposable), reset capability, concurrency ceiling. Automation contains no environment values; a binding references an environment and the worker resolves it. The same specification running against two environments through different bindings is the operational proof that the separation is real.

Secrets

References everywhere — bindings, exploration configuration, test data. Resolution happens once, inside the worker, at job start, from the secret manager, using a short-lived job-scoped token. Values live in memory only, are redacted from worker logs by an output filter, and are never returned in the result callback or placed in a prompt. A deterministic secret-pattern scan runs as a blocking evaluator over every generated artifact before storage.

Concurrency, leases, retries, cancellation

  • Three ceilings compose — global pool, per-environment protection, per-run user setting — and the effective limit is the minimum.
  • Environment leases prevent an exploration session and an execution run colliding on a mutable environment.
  • Retries are classified before attempted: infrastructure retries automatically; assertion failures never; locator failures retry once with healing if policy allows, recorded as a distinct attempt so flakiness stays visible.
  • Cancellation is cooperative at job boundaries and hard after a grace period; partial artifacts are retained and the run is marked partially complete.
D9Evaluators, confidence calibration and failure triage

Evaluator layers

Deterministic

Schema validity, required fields, reference integrity, duplicate detection, traceability completeness, coverage arithmetic, locator syntax, generated-code parse and type check, data values against constraints, secret-pattern scanning.

Derived

Scenario-to-case consistency, case-to-specification consistency, field-to-data compatibility, understanding-to-artifact consistency, contradiction detection, obligation-link validity, oracle-status propagation.

Semantic

Behavioural plausibility, missing edge cases relative to the understanding, expected-result completeness, technique appropriateness, diagnostic interpretation. Confined to judgements no rule can make.

Each evaluator declares its input, the assertions it performs, the evidence it consulted, its decision, severity, confidence contribution and remediation output. Deterministic evaluators run first and can fail an artifact outright; a semantic verdict may never overturn a deterministic one. Evaluator effectiveness is itself measured by whether its verdicts predict downstream failures.

Confidence calibration

Why calibration is a platform component, not a script

The workspace evaluation contains exactly the failure this exists to prevent: a skill was banded high on the strength of a stated rule — that unresolvable paths are dropped rather than guessed — while the implementation did the opposite and mis-reported more than it under-reported. A declared band is a claim about code that may simply be false. The calibration harness is therefore first-class: a maintained ground-truth corpus, per-extractor precision and recall by element type, never averaged into a headline figure, feeding the confidence function as measured priors. The evaluation already built in the workspace is the right instrument, and its refusal to combine scores across evidence classes is the right instinct.

Confidence combines calibrated extractor reliability, evidence strength and independence, inference type, reconciliation status, evaluator verdicts and oracle status. The function is platform-owned and versioned. Bands do not gate autonomous decisions until calibration is reproduced on a second application.
