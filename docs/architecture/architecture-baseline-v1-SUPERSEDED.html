AExecutive Architecture Summary

The platform is not a test generator with a database attached. It is a knowledge system that happens to emit tests. Every architectural decision below follows from that one inversion.

Purpose

Ingest a set of application repositories; build a versioned, evidence-anchored model of what the application is and what it does; explore the running application to confirm and extend that model; reconcile the two; and from the reconciled model generate measurable test coverage, executable Playwright automation, real execution and explainable findings — with every artifact traceable to the evidence that produced it.

Architectural style

A modular monolith control plane with three specialised worker fleets, over a claims-based knowledge core. The control plane owns domain logic, workflow state, governance and the API. Analysis, exploration and execution each run in isolated workers because each has a different resource profile, a different blast radius and a different trust level. There is no microservice decomposition in Phase 1: the domain boundaries are real and enforced in code, but they do not yet justify network boundaries.

The five load-bearing ideas

1 · Claims, not documents

The atomic unit of the fabric is an evidence-supported claim about the application. Graph, domain model, state model and human-readable document are all projections over the claim set — never the source of truth.

2 · Content-derived claim identity

A claim's identity is a hash of its subject, predicate and object. Re-extraction after a commit, and reconciliation between static and runtime, both become set operations on the same key. This single choice makes diffing, staleness and reconciliation nearly free.

3 · Evidence is append-only

A runtime observation that contradicts a static finding does not correct it. It is a second piece of evidence, and the disagreement is the valuable object. Claims are superseded, never mutated.

4 · Intent and binding are separate artifacts

What a test means lives in an Automation Specification. What it runs against lives in an Automation Binding. Self-healing can only reach the binding, so it is structurally incapable of altering intent.

5 · Confidence is computed, never claimed

No model self-reports confidence. The platform derives it from calibrated extractor reliability, evidence strength, inference type, reconciliation status, oracle status and evaluator verdicts.

Core data flow

Repository set at pinned revisions → extractors emit claims with static evidence → claim set forms an Understanding Version → the exploration planner turns unconfirmed claims into an exploration agenda → the crawler provider drives a real browser and returns observations → observation extractors emit claims with runtime evidence → reconciliation compares the two populations by claim identity and assigns each claim a status → the reconciled Understanding Version becomes the sole input to coverage obligations, scenarios, test cases, data requirements and automation specifications → bindings resolve locators, data and environment at run time → execution produces results and artifacts → triage classifies failures before anything is called a defect → findings and coverage feed back as new claims.

The honest headline

Two things in this product are genuinely hard and are not solved by architecture alone: frontend-to-backend relationship extraction and runtime state identity. Your own evaluation already measured the first at P 0.414 / R 0.632 while inventory extraction scored P 1.000 / R 0.982 — enumeration is close to solved, relation is not. The architecture below is shaped around containing that uncertainty rather than hiding it, and §T proposes the experiments that must run before implementation commits.

Attribute conflicts worth naming

Determinism vs. coverage of understanding. Deterministic extraction under-reports; semantic inference over-reports. The architecture resolves this not by choosing but by labelling: both are admitted as claims, tagged with inference type, and weighted differently in confidence and in what they are allowed to gate.

Cost vs. exhaustiveness. "Near-complete coverage" and a bounded token budget are in direct tension. The obligation ledger makes the trade explicit — uncovered obligations are reported rather than silently skipped — but the tension is real and permanent.

Isolation vs. latency. Workers that cannot reach the database must post results through the API, which costs a round trip and forces batching. This is accepted deliberately; see ADR-15.

Inside the platform

Knowledge ownership, claim and evidence model, understanding versioning, exploration planning and state model, reconciliation, coverage obligations, scenario/case/data design, automation specification and binding, execution orchestration, evaluation, confidence, governance, lineage, artifact management, product API and views.

Outside, non-negotiable

The AUT and its repositories; AUT environments; identity provider; secret manager; object storage; model providers. The platform never becomes the system of record for any of these.

Outside, deliberately replaceable

CODE_INTELLIGENCE_PROVIDER, CRAWLER_PROVIDER, LLM providers, MCP servers and external agents. Each sits behind a capability contract with conformance tests. None may hold canonical state.

Not a microservice

Export, evaluation, coverage and triage are modules, not services. They share the transaction boundary with the domain core and have no independent scaling profile. Splitting them would buy nothing and cost consistency.

Bounded contexts

Twelve contexts, reduced from the seventeen candidate areas. Four candidate areas were merged because they share state and lifecycle: Repository Ingestion folds into Static Understanding (it has no independent consumer); Context/Knowledge Fabric and Reconciliation both operate on the same claim store and are separated only by responsibility, not by boundary; Artifact & Evidence Management is a platform-wide capability rather than a domain context; Test Case and Test Data are one context because a data requirement without a test intent is meaningless.

Concerns deliberately kept apart

Evidence and claims. Merging them makes contradiction unrepresentable. Crawler and knowledge. A crawler that owns the model cannot be replaced. Workflow engine and domain semantics. A workflow that knows what a scenario is cannot be reused for exploration. Understanding store and artifact store. Different access patterns, different sizes, different retention. Execution result and finding. One is an observation; the other is a judgement with a cause. Automation spec and binding. Merging them makes safe healing impossible.

Why these layers and not others

  • Orchestration sits above the domain, not inside it. The run/stage machine knows that a stage produced an output and that a gate must be evaluated. It does not know what a scenario is. This is what lets the same machine drive an exploration session, an understanding build and a scenario generation without special cases.
  • The Knowledge Fabric is a layer, not a context. Every domain context reads from it and most write to it. Making it a peer context would put a network or module boundary in the hottest path in the system.
  • Workers do not appear in the domain layer. They are execution substrate. A domain context dispatches work and consumes a result; it never holds a worker reference.
  • The Capability Invoker is the only egress. Every call to a model provider, code intelligence service, crawler or MCP server passes through it. This is simultaneously the security control, the cost control, the provenance recorder and the resilience boundary. Four requirements, one chokepoint — the strongest structural argument in the design.

Environment model

An Environment is a first-class configured entity per workspace: base URL, allowed domains, credentials as secret references, data-safety class (read-only / mutable / disposable), reset capability, and a concurrency ceiling. Automation never contains environment values; a binding references an environment and the worker resolves it. The same automation specification runs against DEV and UAT by swapping bindings, which is the operational proof that the spec/binding split is real rather than nominal.

Secrets

Secrets exist as references (secret://workspace/env/role/credential) everywhere in the platform: in bindings, in exploration configuration, in test data. Resolution happens exactly once, inside the worker process, at job start, from the secret manager, using a short-lived job-scoped token. Resolved values are held in memory, redacted from all worker logs by an output filter, and never returned in the result callback. No secret is ever placed in a prompt; where a credential is genuinely needed for reasoning (rare, and to be challenged), only its reference and type are supplied.

Concurrency, retries, cancellation

  • Three concurrency ceilings compose: a global worker-pool size, a per-environment ceiling (protecting the AUT), and a per-run setting (the user-facing control). The effective limit is the minimum, so the user-facing control is always safe.
  • Environment leases prevent an exploration session and an execution run from colliding on a mutable environment. A lease is held for the duration and released on completion, failure or timeout.
  • Retries are classified before they are attempted. Infrastructure failures retry automatically; assertion failures never do; locator-resolution failures retry once with healing enabled if policy allows, and the retry is recorded as a distinct attempt so flakiness stays visible rather than being smoothed away.
  • Cancellation is cooperative at the job boundary and hard at the process boundary after a grace period; partial artifacts are retained and the run is marked partially complete rather than discarded.

Claim identity — the load-bearing detail

Every claim carries claim_key = hash(subject_key, predicate, object_key), computed from normalised, human-meaningful identifiers — a route template, an endpoint method and path, a symbol's qualified name — never from a database id, file offset or extraction order. Four capabilities fall out of this single choice, each of which would otherwise need bespoke machinery:

  • Understanding diff across commits is a set difference on claim_key.
  • Static and runtime reconciliation is the intersection and difference of two claim populations sharing one key space — the same fact observed twice collides on the same key by construction.
  • Corroboration becomes natural: two extractors producing the same key means two independent evidence records on one claim, which is exactly the signal confidence needs. The corroborated_by mechanism already sketched in skill-test generalises here.
  • Identity stability across regeneration — the flaw in the prototype, where run comparison keys on array indices — disappears, because identity is content-derived at every level including artifacts.
The cost of this choice

Claim keys are only as stable as the normalisation that produces them. Renaming a route, symbol or endpoint changes the key and therefore reads as delete plus create rather than rename. Rename detection is a real and non-trivial follow-on problem. Phase 1 should implement heuristic rename detection for the highest-value node types only — routes and endpoints — and report the remainder honestly as churn. Pretending otherwise would produce misleading understanding diffs, which is worse than an incomplete one.

Two technologies not adopted in Phase 1, and why

Graph database. At the measured scale an in-process graph rebuilt from claims answers a traversal faster than a network round trip to a graph server, with no second system to operate. Adopt one when a measured query need justifies it, not before. The decision is cheaply reversible precisely because the graph is derived.

Vector store. There is currently no retrieval problem that structured claim queries cannot answer better and more explainably. The platform promises deterministic retrieval and traceable evidence; approximate nearest-neighbour search over code chunks pulls against that. Revisit when a specific retrieval failure is demonstrated — most plausibly natural-language search over the understanding for the transcript surface, which is a user-experience feature rather than a core dependency.

Artifact versioning and lineage

Every artifact is a work item with a stable logical identity and an ordered version chain. A version records content, the understanding version it was generated against, typed parent links, the actor and mechanism that produced it (extractor, agent with model and prompt version, or human), evaluator verdicts, confidence, and approval state. Approved versions are immutable. A human edit creates a new version that retains a reference to the machine original and re-derives confidence rather than inheriting it — the prototype behaviour of keeping a machine score on a hand-edited item is a defect this model prevents by construction.

The four measured failure modes, and the architectural rule each produces

Every relationship error in the evaluation traced to one of four causes. Each becomes a binding constraint on relationship extractors:

Unresolved dynamic segments

A template segment collapsed to a wildcard matched every single-segment endpoint — one call site produced six wrong edges. Rule: an unresolvable segment emits a claim with resolution status unresolved and participates in no match. Under-report before mis-reporting, and make the extractor behave the way its stated rule claims.

Framework routing semantics

Literal paths matched a parameterised route the framework would never have selected, because registration order and first-match-wins were not modelled. Rule: route matching is delegated to a framework pack that models the real resolution algorithm, not to generic pattern matching.

Transitive reachability

A screen inherited four endpoints through a runtime import chain it never calls. Rule: direct call edges and transitive reachability are different predicates with different confidence. Reachability alone never produces a CALLS claim.

Injected services and erased types

Five screens produced no edge at all because they receive a running service as a prop and import only types, which vanish at runtime. Rule: statically unresolvable by construction. These are precisely the claims flagged unverified and handed to exploration, where one observed network request settles the question.

Framework packs

The single highest-leverage extensibility point in static understanding. A pack bundles, for one framework family, the route-registration model, the client-call idioms, the component and handler conventions, the validation library shapes and the locator conventions. Packs are versioned and independently evaluable, so support for a new stack is an additive unit of work with a measurable quality figure — not a rewrite of the extractor pipeline. Phase 1 delivers packs for the confirmed AUT stack only; the pack interface is what makes the second stack cheap.

Incremental rescan and change detection

A new revision triggers a diff-scoped rebuild: changed files determine which extractors rerun, and unchanged claims are carried forward by key with their evidence re-anchored to the new revision when the content hash is unchanged. Claims whose supporting evidence no longer resolves become stale and cascade a staleness marker to every artifact derived from them. Staleness is surfaced, never auto-resolved — the decision to regenerate a scenario set after an upstream change belongs to a governance gate, not to a background job.

Because static understanding already knows which endpoint a control invokes, and with what HTTP verb, action risk can be classified before the click happens. Blockers as governed work items

When exploration cannot proceed — a required identifier, a one-time code, a document upload, an entity that must already exist — it does not fail and does not improvise. It emits a Blocker: a durable, attributable, resumable work item stating what is required, why it is required, which resolution strategies were attempted (context lookup, approved data source, synthesis, provisioning) and why each was insufficient. The blocker escalates through the same governance path as any other gate. A supplied value is classified on arrival — secret, personal data, test data or entity reference — and routed accordingly: a value classified secret is stored as a secret reference and never enters an artifact, a log or a prompt, regardless of which field the user typed it into.

Positioning decision

Evaluated against the alternatives of authoritative, advisory, accelerator and retrieval-only: one advisory extractor among several, plus an optional retrieval provider. LLM provider architecture

Model access is separated into five concerns that are frequently and damagingly merged:

  • Task definition — what reasoning is required, expressed in domain terms with a typed output contract. Owned by the domain.
  • Prompt assembly — versioned templates plus a context bundle assembled from claims. Prompt version is recorded on every artifact produced, making generation reproducible in inputs.
  • Model routing — task-to-model policy, allowing a cheaper model for classification and a stronger one for design work, with declared fallbacks.
  • Invocation — the shared gateway: retries, timeouts, structured-output enforcement, deterministic settings where applicable, token accounting against budget, redaction, and provenance capture.
  • Provider adapter — the only component aware of a vendor API.

Two adapters must exist from day one even if only one is used in anger, because a contract with a single implementation is an assumption rather than an abstraction.

MCP, tools and external agents

All external tools reach the platform through the same registry and invoker, carrying declared scopes and a trust level. Two constraints matter more than the mechanics: a tool result is data, never an instruction — tool output cannot cause further tool invocation without a domain-level decision; and every invocation is recorded as provider evidence, so any artifact influenced by an external agent carries that influence in its provenance.

KTest Quality Architecture

Coverage: an obligation ledger, not a percentage

Coverage is the requirement most vulnerable to fabrication, so it is built as bookkeeping rather than judgement. Claims generate obligations; scenarios and cases satisfy them through explicit links; coverage is arithmetic over those links. No model is ever asked what the coverage is, and no model can assert it.

A coverage figure without those three qualifiers is not reportable.

Flagging an unrealistic requirement

"Near-complete" or "exhaustive" coverage is not achievable and should not be promised. Coverage here is coverage of a model that is itself incomplete by measurement — business-rule recall of roughly 0.5 means half the coded rules are absent from the denominator, so a 100% figure against that denominator would be actively misleading. The architecture's contribution is to make the shortfall visible and attributable rather than to eliminate it. This should be reflected in how the product talks about coverage.

Scenario design

An agentic workflow of discrete, independently evaluable steps rather than one generation call: scope selection from obligations; feature decomposition; behaviour analysis from claims; technique selection with a recorded rationale and the evidence supporting it; candidate generation per technique; coverage analysis against the ledger; gap discovery; duplicate and overlap detection by content key; cross-feature and state-path analysis; evaluation; confidence assignment; gate. Techniques are registered strategies — equivalence partitioning, boundary value analysis, decision tables, pairwise, permutation, graph-based path coverage, metamorphic relations, model-based testing — each declaring which claim types it consumes and which obligation types it can satisfy. Adding a technique is a registry entry, not an orchestration change. Notably, a technique is selectable only when the claims it needs exist: decision-table generation requires guard claims; boundary analysis requires constraint claims. This prevents the common failure of applying a technique with no evidential basis, and it means a scenario can honestly carry more than one technique tag where the prototype allowed only one.

Test cases, data requirements and state provisioning

A test case declares data requirements; it never contains resolved data. A requirement names what is needed in model terms — a field value satisfying a constraint claim, an identity holding a role, an entity in a given state, a relationship between entities, or an environment precondition — and resolution happens at bind time against a specific environment. This separation is what allows one approved test case to run against four environments and to remain valid when the data behind it changes.

Resolution follows the declared ladder, with two architectural additions. First, data generation and state provisioning are separate capabilities with separate policies: generating a value that satisfies a constraint is safe and deterministic; creating an application record is a state-changing action subject to the same risk classification and environment policy as exploration. Second, every rung records why the previous rung failed, so a human asked for a value at the end of the ladder sees the same explanation structure as an exploration blocker — the two are the same work-item type.

Evaluator architecture

Evaluators are registered, versioned components with a uniform contract — input artifact and context, assertions performed, evidence consulted, decision, severity, confidence contribution, and remediation output. They compose in three layers, and the ordering matters: deterministic evaluators run first and can fail an artifact outright, which means semantic evaluation is never spent on structurally invalid output.

deterministic

Schema validity, required fields, reference integrity, duplicate detection by content key, traceability completeness, coverage arithmetic, locator syntactic validity, generated-code parse and type check, data values against constraint claims, secret-pattern scanning.

derived

Scenario-to-case consistency, case-to-specification consistency, field-to-data compatibility, claim-to-artifact consistency, contradiction detection across artifacts, obligation-link validity, oracle-status propagation correctness.

semantic

Behavioural plausibility, missing edge cases relative to the claim set, expected-result completeness, technique-appropriateness, diagnostic interpretation of failures. Confined to judgements no rule can make, and never permitted to overturn a deterministic verdict.

Why calibration is architectural, not a development script

The workspace evaluation contains the exact failure this component exists to prevent: the route_endpoint_map skill was banded high on the strength of a stated confidence rule — that unresolvable paths are dropped rather than guessed — while the implementation did the opposite and mis-reported more than it under-reported. A declared band is a claim about code that may simply be false. The calibration harness must therefore be a first-class platform component: a maintained ground-truth corpus, per-extractor precision and recall by claim type, never averaged into a headline figure, feeding the confidence function as measured priors. The evaluation already built in skill-test/ is the right instrument and its refusal to combine scores across evidence classes is the right instinct.

The four axes stay separate in the data model and in the interface: evidence (what supports it), inference type (how it was reached), oracle status (whether expected behaviour is known — applicable only to expectation-bearing claims, never to structural facts), and reconciliation status (whether static and runtime agree). Confidence is a function over all four plus evaluator verdicts; it is not a substitute for any of them, and the review surface shows the axes alongside the score so a user can see why a band was assigned.

Workflow orchestration

The orchestrator owns runs, stages, dependencies, retries, resumption and cancellation. It owns no domain semantics whatsoever — it cannot distinguish a scenario from an exploration session, which is the property that lets one engine drive all of them.

Putting it inside an engine means either querying the engine from the product or duplicating state into the database, and both are worse than owning a small explicit state machine. Tenancy

Recommendation: single-tenant deployment with workspace isolation enforced in the data model. This is the only option that is correct under either answer to the unresolved tenancy question. A single-tenant deployment is simpler to operate, avoids premature isolation machinery, and satisfies the likely enterprise posture; enforcing workspace scoping at the data-access layer from day one means that if multi-tenancy becomes a requirement, the change is deployment topology and identity mapping rather than a data-model migration. Building multi-tenant machinery now would be speculative; building without workspace scoping would be irreversible. This choice avoids both.

Topology

Modular monolith control plane plus three worker fleets. The domain boundaries in §C are real and should be enforced by module structure, dependency rules and a static check — but they do not justify network boundaries in Phase 1. The genuine deployment split is where the resource and trust profiles actually differ, which is between the control plane and the browser-driving workers, not between one domain context and another. Splitting Test Design from Coverage into separate services would add distributed-transaction problems to a system whose hardest problems are epistemic.

The evolution path is explicit: any worker fleet can scale horizontally today; a context can be extracted into a service later if a measured need appears, and the two most plausible candidates are Static Understanding (heavy, bursty, independently versioned) and Execution (already nearly detached). Nothing in the design prevents that, and nothing in Phase 1 pays for it in advance.

RDecision Log

Twenty-four decisions that constrain implementation. Trivial choices are excluded; each entry below either shapes a contract, closes an option, or accepts a named risk.

ADR-01Claims are the canonical unit of application knowledgeaccepted
Context
Understanding must carry provenance, versioning, contradiction and reconciliation status. Documents and graphs represent none of these natively.
Alternatives
Narrative document as truth; graph as truth; per-stage bespoke models.
Rationale
Only a claim-level model can hold two contradictory statements with their evidence and let downstream consumers choose. Everything else forces premature resolution.
Consequences
All projections are derived and rebuildable; no consumer reads raw extractor output; extra normalisation work per extractor.
Risks
Normalisation quality becomes a central concern; a poor ontology propagates everywhere.
Validation
Ontology proven against the real AUT in Validation A before wide implementation.
ADR-02Claim identity is content-derivedaccepted
Context
Diff, reconciliation, corroboration and run comparison all need stable identity across regeneration and across evidence sources.
Alternatives
Surrogate keys with a matching layer; fuzzy similarity matching.
Rationale
Content keys make four separate mechanisms into one set operation and remove the prototype defect of comparing on array position.
Consequences
Normalisation rules become part of the public contract; renames read as delete-plus-create without explicit detection.
Risks
Misleading diffs on refactor-heavy repositories.
Validation
Rename-detection heuristics measured on the AUT history for routes and endpoints.
ADR-03Canonical store is relational; graph is a derived projectionaccepted
Context
Signature queries are graph-shaped; signature guarantees are versioning, provenance and transactionality. Measured graph size is roughly 155 nodes and 228 edges for a full application.
Alternatives
Graph database as canonical; relational only with no projection.
Rationale
Truth needs the relational guarantees; traversal needs a graph shape; at this scale the projection can be in-process, so no second stateful system is required.
Consequences
Existing ontology and query patterns carry forward; a graph engine can be adopted or dropped later without touching truth.
Risks
Traversal ergonomics in the canonical store are worse; projection staleness must be managed.
Validation
Traversal latency measured on projected graphs at 10× the observed AUT size.

The confirmed Phase 1 AUT plus the existing benchmark, with hand-written ground truth for both.
Experiment
Re-run relationship extraction under the new rules; classify every remaining error to a named cause; measure per claim type.
Metrics
Precision, recall, and the residual distribution across the four failure causes.
Threshold
Pass at P ≥ 0.85 with R ≥ 0.60. Marginal between 0.70 and 0.85.
Consequence
Below 0.70, static relationship claims are demoted to hypotheses that may not gate anything, and runtime observation becomes the primary source — reordering the pipeline but not invalidating it.

Hypothesis
The provider materially raises recall or precision on relationship and symbol claims over native extraction alone, at acceptable latency, with anchors precise enough to serve as evidence.

Same repositories and ground truth as Validation A; provider API access and documentation.

Per claim type precision and recall; anchor granularity; ingestion and query latency; revision-addressability; partial-result behaviour.

A deployed AUT environment with seeded data and test identities per role.

State-count variance across identical runs; percentage of static screen claims reached; blockers per session; risk-classification precision and recall.

State-count variance under 10%; ≥ 60% of known screens reached; risk classification recall on destructive actions of 1.00 — no missed destructive action is acceptable.

Reconciliation identifies seeded discrepancies and classifies them correctly, without generating a false-positive volume that would make the output unusable.

A branch of the AUT with deliberately seeded discrepancies: a removed confirmation step, a renamed response property, an endpoint with no UI path.
Experiment
Build understanding, explore, reconcile; compare classifications against the seeded truth and count unseeded mismatches by class.

Seeded-defect detection rate; classification accuracy across the six statuses; unseeded mismatch volume and its class distribution.

Detect ≥ 80% of seeded discrepancies; fewer than 20% of defect candidates are false; unseeded mismatch volume reviewable by a person in under an hour.

High false-positive volume forces reconciliation output to become a diagnostic view rather than a finding source — a significant product reduction that must be known before implementation, not after.

UPhase 1 Architecture Baseline

Recommended architecture, in one statement

A modular monolith control plane over a claims-based knowledge core in a transactional relational store, with derived, rebuildable projections for graph, domain, state, obligation and document views; three isolated worker fleets for analysis, exploration and execution; one capability-invocation path for every external provider; one governance gate serving human and autonomous deciders; and a permanent separation between automation intent and automation binding that makes safe self-healing structural rather than procedural.

Why this architecture

  1. It makes the product's central promise structurally true. Evidence, provenance and contradiction are modelled primitives, not fields added to a document.
  2. It contains the two measured uncertainties — relationship extraction and state identity — behind claim status and confidence, so the platform degrades honestly instead of failing silently.
  3. It turns four hard requirements into one mechanism each: claim identity serves diff, reconciliation, corroboration and comparison; the invoker serves egress control, cost, provenance and resilience; the gate serves human review, autonomy, blockers and oracle escalation.
  4. It defers every expensive technology decision — graph database, vector store, workflow engine, message broker, microservices — behind a seam that makes each reversible on evidence.
  5. It puts isolation where the risk actually is: between the control plane and anything that runs a browser or parses untrusted code.

Phase 1 fixed decisions

Implementation should follow these without further debate: claims as canonical with content-derived identity; append-only evidence; understanding versions pinned to a repository tuple; providers produce observations only; relationship extractors under-report rather than mis-report; state identity is composite; action risk is classified before acting; reconciliation never auto-labels defects; coverage is an obligation ledger; confidence is computed from calibrated priors; specification and binding are separate; the object model is projected from the understanding; one gate implementation; workflow state in the product database; single capability-invocation path; workers hold no database credentials; repository and page content are untrusted; workspace scoping enforced in the data layer.

Phase 1 flexible decisions

Deliberately configurable: graph projection engine (in-process or external); healing auto-apply policy per workspace; model routing per task; exploration budgets, depth and risk-class permissions per environment; generation limits; concurrency ceilings; human or autonomous mode per stage; evaluator set and thresholds per workspace; retention tiers per artifact class; which extractors and framework packs are enabled.

What was deliberately not hard-coded

Code Intelligence

A named port with no binding. The platform is fully functional without it and measures its contribution before depending on it.

Crawler

A narrow actuator-and-sensor contract. The platform owns planning, state identity, claims and safety, so any implementation can sit behind it.

Model provider

Five separated concerns with two adapters required from day one, so the contract is proven rather than assumed.

MCP and external agents

Registry plus the shared invoker; no bespoke integration in any stage.

Graph, vector, queue, workflow engine

All deferred behind ports, each adoptable later on measured need rather than on expectation.

Architecture acceptance criteria

Each is a test the implementation must be able to demonstrate, not a statement of intent.

  • Code Intelligence replaceable — remove the adapter; understanding builds with reduced breadth and no domain code changes.
  • Crawler replaceable — bind a second implementation to CrawlerProvider; the state model, agenda and claims are unaffected.
  • Second model provider — a task runs against either adapter with identical typed output; provenance records which was used.
  • New MCP tool — registered through the registry, invoked through the shared invoker, with no stage-level code.
  • Runtime reconciles with static — an observed network call collides on claim key with its static prediction and produces a match, without a matching heuristic.
  • Artifacts trace to evidence — any finding resolves to repository revision, file, symbol and span, and to the runtime artifacts involved, in one query.
  • Everything versioned — every artifact type has an immutable version chain with typed parents; no orphans exist.
  • One governance layer — human and autonomous decisions on the same artifact produce identical gate packages and audit shapes.
  • Execution scales independently — execution worker count changes with no control-plane change and no restart.
  • Bindings evolve without touching intent — a locator changes; the specification version is unchanged; lineage shows the binding event only.
  • Healing cannot alter intent — attempt to modify an assertion through the healing path; it is structurally unreachable, not merely denied by policy.
  • New evidence sources admissible — a requirements document is registered as a context provider and produces claims that join the same reconciliation without schema change.
  • Insufficient evidence is expressible — an unverified claim yields an insufficient-evidence obligation and a test case with unknown oracle status, and neither is counted as covered or as passing.

Validation required before implementation begins

The smallest sufficient set: Validation A (relationship extraction under the new rules) and Validation C (state identity stability and destructive-action classification). A determines whether static understanding can carry the weight the pipeline places on it; C determines whether exploration is safe to enable and whether its output is stable enough to reconcile against. Validation B should run alongside A if provider access arrives in time, since it changes no architecture either way but does change build priorities. D, E and F can run against the first implemented slice rather than gating its start.

Status

This baseline is complete and internally consistent, and it is ready to be reviewed as the authoritative technical reference. It is not ready to be built from until OD-1 through OD-4 are answered and Validations A and C have run — not because the architecture would change, but because two of its load-bearing assumptions would be confirmed or corrected, and it is far cheaper to learn that now.
